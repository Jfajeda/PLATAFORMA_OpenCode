Sección 1

Introducción y objeto

OpenCode Tracker (título interno «Plataforma de Seguimiento OpenCode — CODANOR») es la aplicación web de panel de control (dashboard) corporativo de CODANOR para el seguimiento del trabajo con la herramienta OpenCode. Está implementada como una SPA (Single Page Application) monolítica en un único archivo HTML (plataforma-seguimiento.html, 2822 líneas), con CSS embebido y JavaScript vanilla sin frameworks externos.

La aplicación integra cuatro bloques funcionales: un Dashboard de métricas, un tablero Kanban de incidencias local, un Gestor de Tiquets conectado al backend Flask de la Plataforma, y un panel de Configuración IA corporativa. Además enlaza con herramientas externas de análisis de código y homogeneización de proyectos.

Arquitectura de servicio en dos puertos

Es crítico entender la separación de responsabilidades entre dos servidores Flask:

PuertoServidorRol
:5003servidor/dashboard_server.pySirve el HTML y los assets estáticos. No tiene base de datos propia.
:5001Plataforma_Seguimiento_Proyectos/servidor/server.pyProvee todas las APIs consumidas en red: tiquets (/api/tiquets/*) y configuración IA corporativa (/api/corp/llm-config).
Audiencia
Personal técnico y de gestión de CODANOR que utiliza la Plataforma de Seguimiento OpenCode. Documento interno — Uso exclusivo CODANOR. v1.0 — 15/11/2026.

Sección 3

Arquitectura y tecnologías

Tipo de aplicación

SPA de un solo archivo. La navegación entre páginas se gestiona con la función showPage(pageId), que alterna la clase active sobre los elementos .page. Dos páginas especiales —el Gestor de Tiquets y la Configuración IA— viven fuera del contenedor principal como overlays position:fixed y ocultan el contenido subyacente con visibility:hidden para no romper el scroll.

Sección 5

Dashboard

Página de inicio con un resumen visual del estado del trabajo. Se compone de cuatro bloques.

Tarjetas de métricas híbrido v1.1

Desde la v1.1, renderDashboard() es asíncrono y usa una fuente de datos híbrida: cuando el backend :5001 está accesible, agrega las métricas desde los tiquets reales del servidor (dashboardFromServer()); si no, cae al Kanban local (dashboardFromLocal()). Un badge de fuente #dashboardSource indica el origen de los datos en cada momento.

Resuelto en v1.1 — métricas conectadas al servidor
Las tarjetas del Dashboard ya reflejan los tiquets del servidor cuando hay conexión. El Kanban local se mantiene como herramienta independiente y actúa de respaldo offline.
TarjetaIDOnline (tiquets :5001)Offline (Kanban local)
Total incidencias#metricTotaltiquets.lengthtickets.length
Completadas#metricDoneestado ∈ {resuelto, cerrado}status === 'done'
En progreso#metricProgressestado ∈ {en_progreso, asignado}status === 'progress'
Prioridad alta#metricHighprioridad ∈ {critica, alta} y no cerradopriority === 'high' && status !== 'done'

Progreso del Manual dinámico v1.1

El progreso ya no está hardcodeado. Se calcula a partir del array MANUAL (fuente única de verdad) mediante renderManualProgress(), que genera el porcentaje, el conteo «N de M» y la cuadrícula de capítulos. Para publicar una nueva versión del manual basta con editar el array en el <script>, sin tocar el HTML.

Resuelto en v1.1 — progreso dinámico
El array MANUAL = { version, meta, capitulos:[{ n, titulo, estado }] } define los capítulos y su estado (nuevo / actualizado / sin etiqueta). El % se deriva de los capítulos con estado.

Contenido actual del manual documentado (16 capítulos): 8 nuevos, 5 actualizados y 3 sin etiqueta.

Actividad Reciente

Lista #activityList poblada desde localStorage['codanor_opencode_activity'] (loadActivity()). Muestra las últimas 10 entradas con formato relativo («Hace X min/h/d», timeAgo()). Estado vacío: #activityEmpty.

Resumen por Tipo

Barras de progreso por tipo (#typeSummary, vía _renderTypeSummary()). En modo online usa los 6 tipos de tiquet (Incidencias, Peticiones, Cambios, Problemas, Vulnerabilidades, Ciberincidentes); en modo offline, los tipos del Kanban local (Bugs, Features, Documentación, Configuración, Rendimiento).

Sección 6

Incidencias (Kanban local)

Tablero Kanban con arrastrar y soltar (drag-and-drop), totalmente local (localStorage). Es un sistema distinto e independiente del Gestor de Tiquets (Sección 7).

Aviso en la interfaz (v1.1)
La página del Kanban muestra ahora un aviso que aclara que es un tablero local (guardado en el navegador) e independiente del Gestor de Tiquets del servidor :5001, para evitar confusión entre ambos sistemas.

Campos de una incidencia

Modelo guardado por saveTicket():

id (T- + timestamp base36) · title · desc · type · priority · status · createdAt · updatedAt.

Tipos y prioridades

TiposPrioridades
bug (Bug) · feature (Feature) · docs (Documentación) · config (Configuración) · perf (Rendimiento) high (Alta) · medium (Media, por defecto) · low (Baja)

Operaciones

  • Crear: «+ Nueva incidencia» → openNewTicketModal() (valores por defecto bug / medium / backlog).
  • Editar: editTicket(id) rellena el modal.
  • Guardar: saveTicket() exige título, registra actividad y re-renderiza.
  • Eliminar: deleteTicket() con confirmación.
  • Avanzar estado: moveTicketForward() o arrastre onDrop().
Datos de ejemplo
En la primera visita se siembran automáticamente 7 incidencias de ejemplo y 3 actividades (seedData()).
Sección 7

Gestor de Tiquets

Módulo integrado con el backend Flask de la Plataforma (plataforma.db, SQLite), con fallback offline. A diferencia del Kanban, los datos se comparten en LAN.

Endpoint base

const TK_API = (() => {
  const h = window.location.hostname;
  const host = (!h || h === 'localhost' || h === '127.0.0.1') ? 'localhost' : h;
  return `http://${host}:5001/api/tiquets`;
})();

El endpoint es LAN-aware: usa window.location.hostname para funcionar desde cualquier PC de la red, nunca localhost hardcodeado.

Modo online / offline

tkDetectarModo() hace un GET /clientes con timeout de 2 s y muestra el indicador #tk-modo-ind: ● Online o ● Offline. En offline usa la caché localStorage['codanor_tiquets_v2']. Reconecta automáticamente con el evento window 'online'.

Tipos, estados y prioridades

TiposEstadosPrioridades

Campos del tiquet

titulo* · descripcion · tipo* · prioridad* · estado · asignado_a · solicitante · control_iso (p. ej. A.16.1.1) · normas_afectadas (array, v1.2) · cvss_score (0–10, solo VUL/CIB) · client_id · app_id. Al crear exige cliente y norma.

CVSS condicionado al tipo (v1.1)
El campo cvss_score se gestiona con tkToggleCvss(): se habilita o deshabilita (y se limpia) según el tipo. Solo aplica a vulnerabilidad y ciberincidente; en otros tipos el valor se envía como null. Antes solo se atenuaba visualmente (opacidad).

Formato de ID (modo offline)

TIK-{NNN}-{client_id}-{app_id}-{DD-MM-AAAA}

Panel de detalle

Muestra tipo, prioridad, estado, asignado, norma, control ISO, descripción y fecha de creación. Incluye Acciones de Seguimiento (pendiente → en_curso → resuelta con barra de progreso y auto-resolución del tiquet cuando todas las acciones están resueltas), Historial de cambios y Comentarios. El SLA se resalta en rojo cuando está vencido.

Prioridad de claves

  2. Clave corporativa (este panel) — compartida en LAN.
  3. Sin clave — se ofrece un prompt manual para copiar a ChatGPT/Claude.

Sección 11

Correcciones aplicadas en v1.1

Los puntos detectados en la revisión inicial (v1.0 del documento) se han abordado en la versión 1.1 de la app. Resumen del estado:

✓ 1. Sistemas de incidencias conectados
El Dashboard es ahora híbrido: agrega las métricas desde los tiquets reales del servidor (:5001) cuando hay conexión, con fallback al Kanban local offline. Un badge #dashboardSource indica la fuente. El Kanban local queda como herramienta independiente, con un aviso en la UI que lo aclara.
✓ 2. Progreso del Manual dinámico
Eliminado el valor hardcodeado. Se calcula desde el array MANUAL con renderManualProgress() (porcentaje, conteo y cuadrícula). Publicar una nueva versión solo requiere editar el array.
✓ 3. CVSS realmente condicionado al tipo
tkToggleCvss() habilita/deshabilita y limpia el campo según el tipo; se envía null salvo para vulnerabilidad/ciberincidente.
✓ 5. Mejoras de paridad y versionado
Incorporada JetBrains Mono (código/IDs/rutas); añadido el proveedor Ollama (Local) al panel de Configuración IA; y la app se versiona explícitamente como OpenCode Tracker v1.1 (visible en el pie del sidebar y en el <head>).
◐ 4. Dependencia del puerto 5001 (mitigada)
La dependencia es intrínseca al diseño LAN (el backend vive en :5001). En v1.1 se mitiga con degradación elegante: el Dashboard cae al Kanban local y la Configuración IA muestra un aviso claro «🔌 :5001 no accesible» con la instrucción para arrancar el servidor.

Pendiente / posibles líneas futuras

  • Migrar completamente el Kanban al backend (hoy sigue siendo local) si se desea una única fuente de datos.
  • Endpoint de estadísticas agregadas en server.py para evitar el cálculo en cliente del Dashboard.
  • Externalizar el array MANUAL a un JSON servido por :5003 (opcional).
