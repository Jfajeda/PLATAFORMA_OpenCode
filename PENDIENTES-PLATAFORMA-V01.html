Nota sobre criticidad

Sección 3

Seguridad

Área de mayor riesgo para la plataforma en producción. Agrupa las vulnerabilidades detectadas por SonarCloud y los accesos necesarios para mantener el análisis continuo activo.

P-09 Regenerar token SonarCloud
Crítica Pendiente Desbloquea P-01

El token de integración con SonarCloud ha caducado. Sin él, el escáner no puede enviar resultados y el panel de analisis-codigo.html muestra datos desactualizados. Este pendiente bloquea la verificación de todos los hotspots de seguridad, incluyendo P-01.

Archivos / sistemas afectados
  • sonar-project.properties
  • analisis-codigo.html (panel)
  • Pipeline CI/CD o script de análisis manual
  • sonarcloud.io → proyecto CODANOR
Impacto si no se resuelve
  • 72 bugs de reliability sin verificar
  • 18 hotspots XSS sin confirmar estado
  • 3 security hotspots sin actualizar
  • Rating Reliability B sin mejorar

Pasos de mejora

  1. Acceder a sonarcloud.io → My Account → Security → Generate Tokens
  2. Crear token nuevo con nombre CODANOR-scanner-2026 y tipo "Global Analysis Token"
  3. Actualizar el token en sonar-project.properties o en la variable de entorno SONAR_TOKEN
  4. Ejecutar el análisis manual: sonar-scanner desde el directorio del proyecto
  5. Verificar que el panel analisis-codigo.html muestra datos actualizados
  6. Registrar el nuevo token en el gestor de contraseñas corporativo
Acción inmediata requerida
Sin este token activo no es posible verificar ni cerrar ningún hotspot de seguridad de P-01. Es el primer pendiente a resolver.
P-01 Corregir 18 innerHTML restantes (XSS)
Crítica Pendiente Requiere P-09

SonarCloud ha detectado 18 usos de innerHTML marcados como security hotspots en los archivos JS de la plataforma. La asignación directa a innerHTML con contenido no saneado es un vector de ataque XSS (Cross-Site Scripting) que puede comprometer sesiones de usuario y datos de los 298 clientes gestionados.

Archivos probablemente afectados
  • js/modules/tiquets.js (9 apps)
  • js/modules/phase2-consulting.js (5 apps)
  • js/modules/phase2-implementation.js
  • js/modules/wiki.js
  • plataforma-seguimiento.html
Riesgo real
  • XSS persistente si el contenido viene de BD
  • XSS reflejado si viene de parámetros URL
  • Afecta a datos de clientes reales (298 clientes)
  • Incumplimiento ISO 27001 A.14 (seguridad desarrollo)

Pasos de mejora

  1. Resolver P-09 primero para obtener la lista exacta de los 18 hotspots con archivo y línea
  2. Para cada hotspot: evaluar si el contenido es interno (no es XSS real) o externo (requiere sanitización)
  3. Sustituir el.innerHTML = val por el.textContent = val cuando el contenido es texto plano
  4. Para HTML que debe renderizarse: usar DOMPurify.sanitize(val) antes de asignar a innerHTML
  5. Añadir DOMPurify (CDN o local) en los index.html de las apps afectadas
  6. Marcar los hotspots que sean falsos positivos como "Safe" en SonarCloud con comentario justificado
  7. Re-ejecutar análisis y verificar que el rating Security sube de A a A+
Patrón de corrección estándar
// ANTES (inseguro):
el.innerHTML = data.comentario;

// DESPUÉS (seguro — solo texto):
el.textContent = data.comentario;

// DESPUÉS (seguro — HTML permitido con DOMPurify):
el.innerHTML = DOMPurify.sanitize(data.comentario);

Alta Pendiente

  • ENS-RD311-2022/js/modules/phase2-consulting.js (TIPO C — patch quirúrgico)
  • RGPD, ISO27701, ISO42001 phase2-consulting.js (TIPO B — sed)
  • ISO9001, ISO14001-2015, ISO14001-2026 phase2-implementation.js (TIPO D — cada uno por separado)
  • TISAX/js/modules/phase2-isms.js (TIPO D)
Métodos destino de la llamada
  • addMeeting() — antes de guardar reunión nueva
  • addTask() — antes de guardar tarea nueva
  • La llamada: if (App._checkSigMembership()) App._toastSigWarning('reuniones');

  6. Editar phase2-isms.js de TISAX (TIPO D)

  8. Verificar que no hay métodos duplicados con el script de detección de AGENTS.md
P-03 Corregir duplicado 8.11 en ISO27001_hacia_ENS.csv
Alta Pendiente Bloquea UNIQUE constraint

El archivo servidor/data/ISO27001_hacia_ENS.csv tiene un error en las líneas 76-77: ambas tienen el código 8.11. La línea 77 debería ser 8.12. Este duplicado impide añadir un constraint UNIQUE a la tabla sig_correspondencias, dejando la integridad de datos desprotegida.

Archivos afectados
  • servidor/data/ISO27001_hacia_ENS.csv — líneas 76-77
  • servidor/plataforma.db — tabla sig_correspondencias
  • servidor/server.py — función de carga de CSVs + DDL
Impacto si no se resuelve
  • Datos duplicados en sig_correspondencias
  • No es posible añadir UNIQUE(hls_id, norma, clausula)
  • Posibles resultados incorrectos en tabla de correspondencias SIG

Pasos de mejora

  1. Abrir servidor/data/ISO27001_hacia_ENS.csv y localizar líneas 76-77
  2. Cambiar el código de la línea 77 de 8.11 a 8.12
  3. En server.py función init_db(): añadir lógica de recarga del CSV en sig_correspondencias (DELETE + INSERT o UPSERT)
  4. Reiniciar Flask para que recargue el CSV corregido
  5. Verificar en SQLite: SELECT clausula, COUNT(*) FROM sig_correspondencias WHERE norma='iso27001' GROUP BY clausula HAVING COUNT(*)>1; — debe devolver 0 filas
  6. Añadir constraint en la definición DDL de sig_correspondencias: UNIQUE(hls_id, norma, clausula)
  7. Invocar POST /api/sig/correspondencias/reload para confirmar recarga limpia

P-08 Acceso total al disco para backup NAS
Alta Bloqueado Requiere acción manual macOS

El script backup-opencode.sh necesita acceso completo al disco para poder leer directorios protegidos por TCC (Transparency, Consent and Control) de macOS. Sin este permiso, el proceso de backup a la NAS CODANOR (SYCODANOR-920) no puede copiar ciertos directorios del sistema.

Contexto técnico
  • Script: backup-opencode.sh (8 modos)
  • NAS: SYCODANOR-920, share: CODANOR
  • Ruta NAS: /Volumes/CODANOR
  • Bloqueado por TCC de macOS (sandboxing)
Acción requerida
  • Ajustes del Sistema → Privacidad y seguridad
  • → Acceso total al disco
  • → Añadir Terminal (o el proceso que ejecuta el script)
  • No es modificable por código — requiere acción del usuario

Pasos de mejora

  1. Abrir Ajustes del Sistema → Privacidad y seguridad → Acceso total al disco
  2. Hacer clic en + y añadir Terminal.app (o iTerm2 si se usa)
  3. Si el backup se ejecuta con cron o launchd, añadir también bash o el script directamente
  4. Verificar que la NAS está montada como Login Item (arrastrar /Volumes/CODANOR a Ajustes → General → Ítems d'inici de sessió)
  5. Ejecutar ./backup-opencode.sh en modo test y verificar que no hay errores TCC
Nota
Este pendiente no puede resolverse mediante código. Requiere acción manual del administrador del equipo macOS.
P-10 Activar Ollama en LAN (OLLAMA_HOST=0.0.0.0)
Alta Bloqueado Bloqueado por firewall MDM

Ollama está activo en el servidor (localhost:11434) pero solo escucha en 127.0.0.1. Para que los equipos de la LAN puedan usarlo como proveedor IA, debe escuchar en 0.0.0.0. El firewall MDM corporativo bloquea la apertura del puerto 11434 hacia la red.

Configuración técnica necesaria
  • OLLAMA_HOST=0.0.0.0 ollama serve
  • O configurar ~/.ollama/config.json con "host": "0.0.0.0"
  • Puerto: 11434 (TCP entrante desde LAN 192.168.0.0/24)
  • Modelos disponibles: qwen2.5-coder:14b, qwen3:8b, llama3.1, gemma3:4b
Soluciones alternativas
  • Proxy inverso Nginx/Caddy en el servidor que reenvíe :11434
  • Solicitar al administrador MDM abrir excepción para el puerto 11434 en la VLAN interna
  • Tunnel SSH desde clientes LAN: ssh -L 11434:localhost:11434 servidor

Pasos de mejora

  1. Solicitar al administrador MDM la apertura del puerto 11434 (TCP) desde la VLAN interna 192.168.0.0/24
  2. Una vez aprobado: añadir OLLAMA_HOST=0.0.0.0 a las variables de entorno del sistema o al script de arranque de Ollama
  3. Reiniciar Ollama: OLLAMA_HOST=0.0.0.0 ollama serve
  4. Verificar desde otro equipo de la LAN: curl http://192.168.0.81:11434/api/version
  5. En la plataforma, configurar proveedor Ollama desde cualquier PC → pestaña Seguimiento → Configuración IA → Proveedor: Ollama

P-15 Ingestar documentos en 9 KBs restantes de Wiki_CODANOR
Baja Pendiente

Wiki_CODANOR (Open WebUI + ChromaDB, Docker en :3000) tiene solo 1 de 10 KBs con documentos ingestados. Los 9 KBs restantes (uno por app ISO/ENS) necesitan los documentos normativos, actas y evidencias correspondientes para que la consulta con IA sea efectiva.

Infraestructura disponible
  • Open WebUI en localhost:3000 (Docker)
  • ChromaDB como vectordb
  • Ollama + OpenRouter conectados
  • 1 KB ya activa como referencia
Documentos a ingestar por KB
  • Norma ISO/ENS en PDF
  • Actas de reunión del proyecto
  • Políticas y procedimientos aprobados
  • Evidencias de auditoría

Pasos de mejora

  1. Acceder a Open WebUI en localhost:3000 → sección Knowledge Bases
  2. Para cada una de las 9 apps: crear una KB con el nombre de la norma
  3. Subir los documentos PDF/DOCX/TXT correspondientes a cada KB
  4. Actualizar las URLs de NotebookLM en wiki.js de cada app si se crea un notebook específico
