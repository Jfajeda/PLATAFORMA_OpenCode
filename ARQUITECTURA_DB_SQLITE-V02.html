Diagrama de relaciones lógicas — plataforma.db

Sin FK nativas
plataforma.db no usa FOREIGN KEY nativas de SQLite. Las relaciones se gestionan lógicamente en server.py. El diagrama muestra relaciones semánticas, no constraints DDL. 
clients (id, app_id)
  └── projects (id, app_id) ──── phase_data (project_id, app_id, phase)
  └── contadores_tiquets (client_id, app_id)
  └── tiquets (client_id, app_id)
        ├── tiquets_historial (tiquet_id)
        ├── tiquets_comentarios (tiquet_id)
        ├── tiquets_acciones (tiquet_id)
        ├── tiquets_adjuntos (tiquet_id)
        └── wiki_articles (source_tiquet_id) ──── wiki_documents

settings (app_id='_global', key='corp_llm_config')
sonar_history (project_key)

risk_projects (id, app_id) ─── [iso27001|ens|lopd]
  └── risk_assets (project_id, app_id)
        └── risk_seguimiento (activo_id)

eipd_projects (id)
  └── eipd_data (project_id, seccion)

Plan de mantenimiento

Checklist diario (automatizable con launchd)

#!/bin/bash
# Verificar integridad
for DB in plataforma.db tracker.db codanor_actas.db ossint.sqlite publications.db; do
  RUTA=$(find ~/Proyectos -name "$DB" 2>/dev/null | head -1)
  [ -f "$RUTA" ] && echo "$DB: $(sqlite3 "$RUTA" 'PRAGMA integrity_check;')"
done

# WAL checkpoint en publications.db (WAL activo sin servidor)
sqlite3 ~/Proyectos/legislacion_monitor-NEW/data/publications.db \
  "PRAGMA wal_checkpoint(FULL);"

# Backup diario plataforma.db
DATE=$(date +%Y%m%d)
sqlite3 ~/Proyectos/Plataforma_Seguimiento_Proyectos/servidor/plataforma.db \
  ".backup /Volumes/CODANOR/backups/plataforma_${DATE}.db"

Checklist semanal

  1. Verificar integridad de las 7 BDs: PRAGMA integrity_check;
  2. Comprobar tamaño de plataforma.db — alerta si supera 50 MB
  3. Revisar WAL activos: ls -lh *.db-wal *.db-shm en todos los proyectos
  4. Ejecutar VACUUM en BDs con muchas inserciones/borrados: PRAGMA vacuum;
  5. Validar backups de plataforma.db y tracker.db en NAS Synology
  6. Añadir backups de codanor_actas.db, chroma.sqlite3 y webui.db al script NAS

Checklist mensual

  1. Purgar backups de plataforma.db con más de 30 días — conservar los 3 más recientes de cada mes
  2. Actualizar este documento con el recuento de registros real
  3. Verificar que las tablas risk_* y eipd_* se han poblado — si siguen vacías, coordinar migración IndexedDB → servidor
  4. Revisar sonar_history — ejecutar un análisis SonarCloud y verificar que el endpoint /api/sonar/save guarda datos
  5. Ejecutar PRAGMA optimize; en plataforma.db para actualizar estadísticas del planificador de consultas
  6. Auditar logs de acceso Flask — verificar no hay accesos anómalos a la API en LAN

Restauración de emergencia — plataforma.db

# 1. Detener el servidor Flask
pkill -f "python3 server.py"

# 2. Hacer backup del estado actual (aunque esté dañado)
cp plataforma.db plataforma_EMERGENCY_$(date +%Y%m%d_%H%M%S).db

# 3. Restaurar desde el backup más reciente del NAS

Sección 9

Mejoras propuestas — plataforma.db

P1 — Críticas

1. Índice parcial para wiki_article_id
CREATE INDEX idx_tiquets_wiki ON tiquets(wiki_article_id)
WHERE wiki_article_id IS NOT NULL;
Actualmente cada consulta de tiquets cerrados con artículo wiki hace full-scan de la tabla.
2. FOREIGN KEYs nativas en DDL
Añadir FOREIGN KEY ... ON DELETE CASCADE en las tablas de tiquets. Activar con PRAGMA foreign_keys = ON; en cada conexión Flask. Actualmente solo hay integridad lógica en server.py.
3. Índice compuesto para SLA vencido
CREATE INDEX idx_tiquets_sla ON tiquets(sla_vencimiento, estado)
WHERE sla_vencimiento IS NOT NULL;
Para alertas de SLA vencido en el panel de tiquets.
4. Migración datos risk_* y eipd_* desde IndexedDB
Las 5 tablas de riesgos están vacías. Cada usuario con datos en IndexedDB debe acceder al dashboard correspondiente y pulsar "Migrar a servidor". Crear procedimiento de migración masiva para todos los proyectos activos.

P2 — Alta prioridad

5. Soft delete (RGPD Art. 17)
Añadir columna deleted_at TEXT DEFAULT NULL en tiquets para derecho al olvido. Sustituir DELETE por UPDATE con timestamp.
6. Autenticación JWT en la API Flask
La API está completamente abierta en LAN. Implementar flask-jwt-extended con tokens de corta duración. Crítico si la red LAN va a crecer o si se expone a internet.
7. Backup automatizado de las 5 BDs sin respaldo
codanor_actas.db, ossint.sqlite, publications.db, chroma.sqlite3 y webui.db no tienen backup. Añadir al script backup-opencode.sh del NAS Synology.
8. Tabla de alertas SLA
tiquets_sla_alertas — monitorear vencimientos y notificar vía email/webhook/UI. Evita que los SLAs venzan sin visibilidad.

P3 — Media prioridad

9. Índice compuesto principal para el panel
CREATE INDEX idx_tiquets_main ON tiquets(client_id, app_id, estado, creado_en DESC);
Cubre el 90% de las consultas del panel de tiquets (filtro + orden).
10. VACUUM automático semestral
Añadir endpoint POST /admin/vacuum en server.py que ejecute VACUUM y ANALYZE en plataforma.db. Programar vía launchd cada 6 meses o cuando el tamaño supere 100 MB.
11. Poblar sonar_history
El endpoint /api/sonar/save existe pero nunca se ha llamado. Integrar en el flujo de /sonar (slash command de OpenCode) para que cada análisis SonarCloud guarde el resultado histórico.

P4 — Largo plazo

12. Tabla audit_log centralizada
Extender la auditoría campo a campo (actualmente solo en tiquets_historial) a clients, projects y phase_data. Necesario para ISO 27001 A.16 completo.
13. Columnas materializadas en phase_data
Añadir progress INTEGER, total_meetings INTEGER, total_tasks INTEGER en phase_data para KPIs sin parsear JSON. Mejoraría el rendimiento del dashboard.
14. Sharding por app_id cuando > 500 MB
Si plataforma.db supera 500 MB o GET /phase tarda más de 200ms, evaluar separar en BDs por app_id. Trigger: monitorear con PRAGMA page_count * page_size;

Consultas SQLite de referencia

-- Tiquets abiertos por cliente y norma
SELECT t.tiquet_id, t.titulo, t.estado, t.prioridad, t.creado_en
FROM tiquets t
WHERE t.client_id = 'CLI-001' AND t.app_id = 'iso27001'
  AND t.estado NOT IN ('resuelto','cerrado')
ORDER BY t.prioridad ASC, t.creado_en ASC;

-- SLA vencidos
SELECT tiquet_id, titulo, sla_vencimiento, estado
FROM tiquets
WHERE sla_vencimiento < datetime('now')
  AND estado NOT IN ('resuelto','cerrado')
ORDER BY sla_vencimiento ASC;

-- Tiquets sin artículo wiki con estado cerrado
SELECT tiquet_id, titulo, fecha_resolucion
FROM tiquets
WHERE estado = 'cerrado' AND wiki_article_id IS NULL
ORDER BY fecha_resolucion DESC;

-- Resumen de registros por tabla
SELECT name, (SELECT COUNT(*) FROM sqlite_master WHERE type='table') AS total_tables
FROM sqlite_master WHERE type='table'
UNION ALL
SELECT 'clients - filas'   , COUNT(*) FROM clients
UNION ALL
SELECT 'projects - filas'  , COUNT(*) FROM projects
UNION ALL
SELECT 'tiquets - filas'   , COUNT(*) FROM tiquets
UNION ALL
SELECT 'risk_projects'     , COUNT(*) FROM risk_projects
UNION ALL
SELECT 'wiki_articles'     , COUNT(*) FROM wiki_articles;

-- Estadísticas WAL
PRAGMA wal_checkpoint;
PRAGMA page_count;
PRAGMA page_size;
PRAGMA freelist_count;

Unificación futura del ecosistema de BDs

El ecosistema tiene actualmente 7 BDs independientes. A medida que el proyecto crezca, conviene valorar la unificación progresiva en plataforma.db para reducir la complejidad operativa.

Candidatas a integración

BDCandidataPrioridadConsideraciones
codanor_actas.dbSíMedia7 tablas fácilmente migrables. Evitaría silo de datos. Requiere adaptar el servidor de actas para usar plataforma.db.
ossint.sqliteSíBajaBD vacía — crear las tablas en plataforma.db directamente cuando el proyecto OSSINT avance.
publications.dbPosibleBajaTabla única, fácil de migrar. Pero el monitor de legislación es un proceso independiente — mejor mantener BD separada.
tracker.dbRevisarMedia5 tablas. Mismo servidor Flask — podría integrarse pero implica refactorizar el app.py del tracker.

Hoja de ruta de integración

  1. Corto plazo: Añadir backup de codanor_actas.db al script NAS. Activar WAL en ossint.sqlite y codanor_actas.db.
  2. Medio plazo: Migrar ossint.sqlite a plataforma.db cuando el proyecto OSSINT pase de dev a producción.
  3. Largo plazo: Evaluar migración de codanor_actas.db cuando se renueve el módulo de actas de la Plataforma.
  4. Nunca: chroma.sqlite3 y webui.db — gestionadas por sus respectivos motores.

Glosario

Glosario de términos

TérminoDefinición
plataforma.dbBase de datos SQLite principal del ecosistema CODANOR. 19 tablas, 3,3 MB, modo WAL, Flask :5001. Fuente de verdad de todos los módulos de la Plataforma ISO/ENS.
WALWrite-Ahead Logging. Modo de SQLite que permite lecturas concurrentes durante escrituras. Activo en plataforma.db, tracker.db y chroma.sqlite3. Genera archivos .db-wal y .db-shm.
phase_dataTabla de almacenamiento genérico para todas las fases de las 9 apps ISO/ENS. PK compuesta: (project_id, app_id, phase). La clave phase es libre: phase1, gap, soa, mapa_procesos...
PHASE_KEYSConstante en store.js de cada app. Lista las claves de phase_data a sincronizar desde Flask al abrir un proyecto. Garantiza que todos los PCs de la LAN vean los mismos datos.
app_idIdentificador de la norma/aplicación. Valores: iso27001, ens, rgpd, iso27701, iso42001, iso14001, iso9001, tisax. Columna clave en casi todas las tablas para aislar datos entre normas.
FK nativaFOREIGN KEY declarada en el DDL de SQLite. plataforma.db no las usa — la integridad referencial se gestiona lógicamente en server.py. Activar con PRAGMA foreign_keys = ON;
Magerit v3Metodología de análisis y gestión de riesgos del CCN. El esquema de risk_assets tiene 37 columnas siguiendo el modelo Magerit v3 + dimensiones ENS (impacto_aut, impacto_traz).
EIPDEvaluación de Impacto en Protección de Datos (DPIA). Módulo LOPD-RGPD en plataforma.db. Tablas eipd_projects y eipd_data almacenan las secciones como JSON.
ChromaDBBase de datos vectorial para búsqueda semántica (RAG). Almacenada en chroma.sqlite3. Gestionada exclusivamente por Open-WebUI — no manipular directamente con sqlite3.
RAGRetrieval-Augmented Generation. Técnica que combina búsqueda en ChromaDB con generación de texto por LLM. Usada en Wiki_CODANOR para consultar documentación corporativa.
soft deleteTécnica de borrado lógico — en lugar de DELETE, se marca el registro con deleted_at = timestamp. Requerido por RGPD Art. 17 (derecho al olvido) con trazabilidad de cuándo se "borró".
VACUUMComando SQLite que reconstruye la BD, libera espacio fragmentado y reduce el tamaño del archivo. Recomendado semestralmente. PRAGMA vacuum; o ejecutar al arrancar Flask tras muchas operaciones.
XOR+base64Técnica de ofuscación de la clave LLM corporativa. La clave API se cifra con XOR(clave fija) + base64 antes de guardarse en settings. Clave XOR fija desde v20261003a: codanor_llm_2026_xor_key_fixed!!
IndexedDBBase de datos del navegador web. Solo accesible desde el navegador del mismo PC — no compatible con LAN multiusuario. Los módulos de riesgos han migrado de IndexedDB a plataforma.db.
shardingTécnica de particionado de datos en múltiples BDs. Para plataforma.db: separar por app_id si supera 500 MB o si las consultas GET /phase tardan más de 200ms.
